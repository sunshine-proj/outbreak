Phase 2 is written the same way as Phase 1: all C++, nothing compiled, run or tested in Unreal. Every Phase 2 task is marked [-] in ROADMAP.md, and the blocker table now lists Phase 2 verification.

Your answer on replication is logged as decision D-006, and open decision O-006 is closed. Clients send requests to the server, and the server checks each one (fire rate, ammo, reload state, and that the shot starts near the shooter's eyes). It then applies damage and tells every machine to play the effects. Health and weapon state are copied to all players.

What's implemented

Area	Files
Weapon data	OutbreakWeaponDefinition.h: magazine, reload time, aim zoom, effects, and a list of fire modes (damage, fire rate, spread, recoil, range). Asset validation catches bad settings in the editor.
Ammo types	OutbreakAmmoTypeDefinition.h: damage multiplier, damage type, optional explosion radius, impact effects.
Firing	OutbreakFireBehavior.h: each fire mode is either hitscan or projectile. OutbreakProjectile.h is the projectile itself, visible to all players.
Weapon component	OutbreakWeaponComponent.h: picking up and switching weapons, fire rate, spread that grows as you fire, recoil, aiming, reload, auto-reload when empty, switching fire mode and ammo type, ammo reserves.
Health and damage	OutbreakHealthComponent.h: Alive → Incapacitated → Dead, with per-damage-type multipliers. Four damage types (ballistic, armour-piercing, explosive, energy) in OutbreakDamageTypes.h. Damage goes through the engine's standard damage system, so any actor can receive it.
Test target	OutbreakCombatTestTarget.h: hostile team by default, visible to AI sight, shrinks briefly when hit, comes back after it's destroyed. Set it to the neutral team for a plain damageable target.
Player	The character now has health, weapons and a team; it binds the weapon keys, kicks the view when hit, zooms when aiming, and disables movement, input and weapons on death. The HUD shows real health, ammo and a weapon line, e.g. Rifle | Automatic | Standard.
Tests	13 new automation tests in OutbreakWeaponTests.cpp and OutbreakHealthTests.cpp.
Fixes to Phase 1 code

Test helper: the helper never prepared the test world for play, so spawned actors skipped part of their setup and the Phase 1 movement-settings tests would have failed. It's fixed in OutbreakTestWorld.h.
Client HUD: the HUD hookup only ran on the server, so a client player would never see their HUD update. It now runs on every machine.
Docs: Docs/Phase2-EditorSetup.md covers the 4 new input actions, example rifle, launcher and ammo assets, the combat test map, and a checklist for checking it by hand. That checklist includes a 2-player client run to check that the server stays in control. I also added decision D-007 (how weapon data is structured) to the roadmap.

Risks and gaps

Compiling: this is about 2,000 lines that have never been compiled, so expect some fixes on the first build. The asset validation code needs UE 5.3 or later, which ties into the open engine-version decision (O-004).
Not covered by automated tests: the test world's clock never advances, so hitscan traces, projectiles, timed reloads and automatic fire can only be checked by hand in the editor.
Client ammo: a remote client's ammo count updates only after the server replies. Recoil is applied on the client straight away.
No meshes or real effects: there are no weapon models, and muzzle flash and impact effects need Niagara assets to be assigned.
Nothing is committed. The next roadmap step is Phase 3 (squad architecture), but open decision O-001 (where squad size limits are configured) has to be settled first.

Your answer on squad limits is logged as D-008, and open decision O-001 is closed:

Project limits: min 2, default 4, max 6, in Project Settings (saved to DefaultGame.ini).

What's implemented

Area	Files
Shared character base	OutbreakCharacter.h: movement, sprint and crouch, health, weapons, squad membership, team and death handling. The player and teammates both use it; the player keeps its camera, input, interaction and aim.
AI teammate	OutbreakTeammateCharacter.h: possessed by a plain AI controller and stands still until Phase 4.
Squad member	OutbreakSquadMemberComponent.h: on the player and every teammate. Holds an ID unique within the squad, a name and a role. Status (Active / Incapacitated / Dead) comes from health; it also reports health fraction, position and whether the member can take orders.
Squad	OutbreakSquadComponent.h: a dynamic list of members with no fixed size. Handles registration, removal (including when a member is destroyed), size limits, composition checks, status queries and events. It lives on the new OutbreakPlayerState.h, so it survives the player's death.
Configuration	OutbreakSquadSettings.h holds the project limits. OutbreakSquadConfiguration.h sets a mission's size, named teammates and a filler teammate for remaining slots. OutbreakSquadRoleDefinition.h gives each role default weapons and ammo; a member's own equipment replaces the role's.
Spawning	The game mode builds the squad the first time the player spawns. Adding ?SquadSize=N to the map URL changes the size for quick tests, still within the limits.
Tests	7 tests in OutbreakSquadTests.cpp, including the full 2–6 squad-size matrix with the player counted.

What's implemented

Area	Files
Squad AI controller	OutbreakSquadAIController.h: sight perception, tracking the nearest visible hostile, checking whether the current order is done, choosing a behaviour and the place to move to. Teammates steer around each other in crowds.
Priority rules (D-011)	OutbreakTeammateBehaviorTypes.h: survival > explicit order > threat > staying in position > idle, as in AGENTS.md §6.1. The order can be changed per AI config. Teammates shoot visible hostiles whatever they're doing, so Hold or Move doesn't leave them defenceless.
BT services	BTService_OutbreakUpdateBehavior.h runs the decision step. BTService_OutbreakTeammateCombat.h aims, fires and reloads automatically, going through the same server-checked weapon requests as the player.
AI config	OutbreakTeammateAIConfig.h: perception, priorities, follow distances, when orders count as done, and combat settings, with validation.
Commands	OutbreakSquadCommandTypes.h: Follow, Hold, Move, Regroup and Attack as structured data. Each order is Active, Completed, Cancelled or Failed. Move becomes Hold on arrival, Regroup ends near the player, Attack ends when the target dies, and a downed teammate's order fails.
Distribution	The squad component sends orders to the whole squad, one teammate or a selection, checked on the server. The player can never be ordered.
Command interface	OutbreakSquadCommandComponent.h: select by slot, add or remove from the selection, select all. Move and Attack take their target from the crosshair. A squad panel on the HUD shows each teammate's order, activity, health or KIA, and distance.
Follow positions	OutbreakSquadPositioning.h: a separate spot behind the player for each teammate, for any squad size.
Tests	13 new tests in OutbreakTeammateAITests.cpp and OutbreakSquadCommandTests.cpp, including commands for every squad size from 2 to 6.
Docs: Docs/Phase4-EditorSetup.md covers:

Blackboard: the exact key names and types.

Navigation: navmesh setup.
Input: 9 squad input actions. Member keys F1–F5 use a value per key, so a bigger squad needs only more keys, not code.
Test map: an open area and a narrow passage.
Checklist: to run with squads of 2, 4 and 6.
Risks and gaps

Compiling: this is now 4 phases of code that has never been compiled. Phase 4 is the most engine-API-heavy part (AI controller, perception, Behavior Tree nodes, crowd following), so expect fixes on the first build.
Not covered by automated tests: the test world has no navmesh and runs no AI, so actual movement, perception and shooting can only be checked by hand in the editor.
Friendly fire: teammates may shoot through the player or each other.
Sight only: teammates react to what they see; hearing comes in Phase 8.

Shared interface: teammate and enemy controllers now both implement a small IOutbreakAIAgent interface (OutbreakAIAgent.h). One update service and one combat service drive both, so the aim/fire/reload logic exists only once.
Renames: the combat service is now UBTService_OutbreakCombat ("Outbreak: Combat"), the update service's display name is now "Outbreak: Update Behavior", and the combat rules namespace is now OutbreakAICombat.
Git and the Phase 4 guide: I used git mv for the renames, so they're staged, and updated the Phase 4 guide to match.
What's implemented

Area	Files
Enemy character	OutbreakEnemyCharacter.h: built on the shared soldier base. Health, resistances, movement and weapon come from its definition. Its state is copied to all players for animation Blueprints, and dead enemies stop blocking and are removed after a delay.
Enemy definition	OutbreakEnemyDefinition.h: every enemy setting is data (health, movement, weapon, sight and hearing, alert time, patrol, combat range, targeting weights), with validation.
Enemy AI controller	OutbreakEnemyAIController.h: sight and hearing as separate senses. Picks the most attractive visible hostile, switches between Idle, Patrol, Alerted and Combat, and keeps within its combat range. Pure rules	OutbreakEnemyTypes.h: state selection, target scoring and combat positioning, with no actors involved, so they're unit-tested.
Patrol	OutbreakPatrolRoute.h: points you drag in the viewport; the route either loops or goes back and forth.
Gunfire noise	Every shot reports an AI hearing event, with loudness and range set on the weapon. This is the minimal hook; Phase 8 replaces it.
Debugging	outbreak.AI.DebugEnemies 1 draws each enemy's sight cone (coloured by state), hearing radius, state, target, destination and alert point.

What's implemented

Area	Files
Mission data	OutbreakMissionDefinition.h: name, briefing, the mission's squad configuration (which wins over the game mode's), an ordered list of objectives, fail-on-death setting, restart delay and update interval, with validation.
Objectives	OutbreakObjective.h is the base: Activate, Evaluate, Deactivate, plus description and progress text. Fresh copies are made each play, so the asset is never changed at runtime.
Reach Location	OutbreakReachLocationObjective.h: done when a living player reaches an OutbreakMissionMarker with the matching ID; shows the distance. A missing marker fails the mission loudly instead of leaving it stuck.
Eliminate Target	OutbreakEliminateTargetObjective.h: done when every actor with the given tag is dead or destroyed; shows "2 / 5".
Mission subsystem	OutbreakMissionSubsystem.h: runs on the server. It checks the current objective every 0.25 s, advances through the list, completes or fails the mission, and restarts the level after the delay. The mission fails when every player is dead, so one player down in co-op isn't a failure.
Client display	OutbreakGameState.h copies the mission status to every client. The HUD shows the current objective at the top centre and MISSION COMPLETE or MISSION FAILED with the reason in the middle.
Game mode	Sets up the mission when the game starts, starts it when play begins, and registers each player when they spawn.
Tests	4 tests in OutbreakMissionTests.cpp.
Docs: Docs/Phase6-EditorSetup.md covers:

Level: building the greybox prototype level (deployment yard, approach, walled compound with a gate and a narrow side passage, exit), plus navmesh.
Enemies: placement and patrols.
Mission: the marker and the mission asset.
Acceptance checks: completing the mission with squads of 2, 4 and 6, player death failing it, squad movement through the narrow passage, and the 2-player client case.
Risks and gaps

Compiling: this is about 7,000 lines across six phases that have never been compiled. The first build will very likely need a round of fixes, and the whole automated test suite should be run after it.
Editor work: the editor half is now large. The six setup guides list every asset and the level, and they're meant to be worked through in order.
Simple flow: there's no briefing or results screen, the level just restarts, and objectives run strictly one after another (all Phase 11).
Respawning targets: combat test targets used as mission targets must have Respawn Delay 0, or the objective never completes.
